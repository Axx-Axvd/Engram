# Проектный документ для разработки MVP
## Рабочее название: MARES / слой проектной памяти для долгих AI-проектов

> Этот документ предназначен как исходная спецификация для Claude Code, Codex или другого помощника-разработчика.
> Его задача — зафиксировать проблему, идею решения, границы MVP, архитектуру, модель данных, технический стек и план реализации.
> Название проекта можно поменять позже. Внутри документа важнее сама суть.

---

## 1. Краткая суть проекта

Проект представляет собой **систему управления проектной памятью** для длинных AI-проектов.

Идея в том, что языковая модель или агентная команда **не должны помнить весь проект внутри одного диалога**. Вместо этого знания о проекте должны храниться **вне модели** — в виде **связанных артефактов**:

- требования;
- пользовательские истории;
- задачи;
- тест-кейсы;
- запросы на изменение;
- журнал решений;
- версии артефактов;
- связи между артефактами.

Когда пользователь просит выполнить новую задачу, система не подает модели весь проект целиком. Она подбирает только те артефакты, которые относятся к нужной области проекта, и строит на их основе рабочий контекст.

---

## 2. Проблема, которую поднимает проект

### 2.1 Главная проблема

Реальные проекты длятся долго, постоянно меняются и порождают большое количество знаний:
- интервью и исходные описания;
- требования;
- уточнения;
- пользовательские истории;
- задачи;
- архитектурные решения;
- тесты;
- исправления;
- запросы на изменение.

Если вести такой проект только как длинный диалог с LLM, возникают серьезные проблемы.

### 2.2 Подпроблемы

#### 1. Ограничение контекста
Даже большое окно контекста не подходит как единственная память проекта. Через некоторое время информации становится слишком много.

#### 2. Шум и забывание
Чем длиннее история, тем труднее модели опираться на действительно важные фрагменты. Старые договоренности могут теряться или смешиваться с новыми.

#### 3. Расхождение артефактов
Требование могло измениться, а связанные:
- задачи,
- тесты,
- пользовательские истории,
- документы
не были обновлены.

#### 4. Плохой анализ изменений
Когда приходит запрос на изменение, трудно понять:
- что именно он затрагивает;
- какие части проекта надо обновить;
- где появятся противоречия.

#### 5. Высокая стоимость токенов
Если несколько агентов на каждом шаге получают большой кусок проекта, система быстро начинает тратить слишком много токенов и времени.

### 2.3 Суть проблемы в одном абзаце

Нужна система, которая будет не просто вызывать модели, а **управлять проектной памятью**, хранить знания о проекте в устойчивом виде и подбирать **минимально необходимый контекст** для конкретной задачи.

---

## 3. Предлагаемое решение

### 3.1 Общая идея

Нужно построить **управляющий слой над LLM/агентами**, который будет:

1. хранить знания о проекте вне модели;
2. представлять их как связанные артефакты;
3. выбирать релевантные артефакты под конкретную задачу;
4. сохранять результаты работы модели обратно в систему;
5. поддерживать версии, связи и проверки согласованности.

### 3.2 Простое описание

Пользователь пишет:
> “Измени поведение корзины на фронтенде.”

Система должна:
1. понять, что это изменение существующей части проекта;
2. найти связанные требования по корзине;
3. найти связанные пользовательские истории, задачи, тесты и изменения;
4. собрать из них небольшой рабочий контекст;
5. отдать этот контекст модели;
6. получить от модели новое содержание или предложения;
7. оформить результат как новый или обновленный артефакт;
8. отметить, какие другие артефакты теперь тоже требуют обновления или проверки.

### 3.3 Ключевая идея

**Модель делает локальное рассуждение.  
Система управляет памятью проекта.  
Артефакты являются памятью проекта.**

---

## 4. Что должно быть сделано

Проект нужно строить не как “еще одного агента”, а как набор прикладных модулей.

### 4.1 Обязательные части системы

#### 1. Хранилище артефактов
Система должна хранить:
- тип артефакта;
- содержимое;
- статус;
- версию;
- дату создания;
- дату изменения;
- источник;
- автора изменения;
- связи с другими артефактами.

#### 2. Граф связей
Система должна уметь хранить связи между артефактами:
- требование связано с пользовательской историей;
- история связана с задачей;
- задача связана с тестом;
- запрос на изменение меняет конкретные артефакты.

#### 3. Модуль выбора контекста
Система должна уметь отвечать на вопрос:
> “Какие артефакты нужны модели именно сейчас?”

#### 4. Оркестратор шагов
Система должна поддерживать рабочие сценарии:
- прием описания проекта;
- уточнение;
- формализация требований;
- генерация пользовательских историй;
- генерация тест-кейсов;
- обработка запроса на изменение;
- проверка согласованности.

#### 5. Модуль проверки согласованности
Система должна проверять:
- есть ли разорванные связи;
- есть ли дубликаты;
- есть ли требования без историй;
- есть ли истории без задач;
- есть ли требования без тестов;
- есть ли изменения, не отраженные в связанных артефактах.

#### 6. Версионирование и журнал изменений
При каждом изменении система должна:
- создавать новую версию артефакта;
- хранить старую;
- сохранять причину изменения;
- показывать активную версию.

## 5. Границы MVP

### 5.1 Что MVP должен доказать

MVP не обязан покрывать весь жизненный цикл разработки. Он должен доказать одну вещь:

> Проектные знания можно вынести из модели в виде связанных артефактов, а затем использовать их для точного подбора контекста и анализа изменений.

### 5.2 Самый реалистичный MVP-сценарий

Рекомендуемый сценарий MVP:

**Описание проекта -> требования -> пользовательские истории -> тест-кейсы -> запрос на изменение -> анализ влияния изменения -> обновление/проверка**

### 5.3 Что входит в MVP

В MVP должны входить:

- прием исходного описания проекта;
- генерация структурированных требований;
- генерация пользовательских историй;
- генерация тест-кейсов;
- сохранение этих сущностей как артефактов;
- связи между ними;
- обработка одного change request;
- показ затронутых артефактов;
- базовая проверка согласованности;
- простой интерфейс для демонстрации сценария.

### 5.4 Что НЕ входит в MVP

В MVP не входят:

- полноценная замена команды разработки;
- автоматическое написание и деплой большого кода;
- сложная агентная организация;
- роли с глубокими правами доступа;
- продвинутая MLOps-инфраструктура;
- интеграции с Jira, GitHub, Confluence, Slack;
- прод-уровневая безопасность;
- графическая UML-генерация как обязательный элемент;
- enterprise-ready UI.

## 6. Ценность проекта

### 6.1 Ценность для пользователя и бизнеса

Проект потенциально дает следующие преимущества:

1. **Снижение хаоса** в длинных AI-проектах.
2. **Сохранение знаний о проекте** между шагами и сессиями.
3. **Меньше ручной координации** между требованиями, задачами и тестами.
4. **Лучший анализ изменений**: понятно, что затронуто и что нужно пересмотреть.
5. **Экономия контекста и токенов**: модели не нужно читать весь проект.
6. **Более прозрачная работа агентов**: понятно, что из чего выросло и где что изменилось.

### 6.2 Что здесь не является ценностью

Ценность не в том, что:
- модель умеет писать текст;
- агент складывает файлы в папки;
- есть просто набор markdown-документов.

Ценность именно в том, что:
- артефакты связаны;
- есть активные версии;
- система умеет подбирать релевантный контекст;
- система умеет анализировать последствия изменений.

## 7. Минимальная архитектура MVP

### 7.1 Общая схема

Пользователь -> API/интерфейс -> Оркестратор -> Выбор контекста -> LLM -> Сохранение артефакта -> Проверка связей и версий

### 7.2 Компоненты MVP

#### 1. API / интерфейс
Простой интерфейс для:
- загрузки описания проекта;
- запуска workflow;
- просмотра артефактов;
- подачи запроса на изменение.

#### 2. Оркестратор
Код, который определяет:
- какой сценарий сейчас выполняется;
- какой шаблон запроса нужен;
- какие шаги идут дальше.

#### 3. Адаптер модели
Отдельный модуль для вызова LLM:
- Anthropic;
- OpenAI;
- позже возможен локальный вариант.

#### 4. Хранилище артефактов
База данных или структурированное хранилище.

#### 5. Хранилище связей
Таблица связей или отдельный графовый слой.

#### 6. Выбор контекста
Логика поиска связанных артефактов и сборки минимального контекста.

#### 7. Проверка согласованности
Набор правил проверки после каждого изменения.

---

## 8. Модель артефактов для MVP

### 8.1 Обязательные типы артефактов

1. **Requirement** — требование  
2. **UserStory** — пользовательская история  
3. **Task** — задача / backlog item  
4. **TestCase** — тест-кейс  
5. **ChangeRequest** — запрос на изменение  
6. **DecisionRecord** — запись о решении (желательно)

### 8.2 Общая структура артефакта

Каждый артефакт должен иметь:

- `id`
- `type`
- `title`
- `content`
- `status`
- `version`
- `source_ref`
- `created_at`
- `updated_at`
- `created_by`
- `updated_by`

### 8.3 Пример статусов

Для Requirement:
- draft
- reviewed
- approved
- changed
- archived

Для ChangeRequest:
- proposed
- in_review
- approved
- rejected
- applied

---

## 9. Типы связей между артефактами

Нужен минимальный набор связей.

### 9.1 Базовые типы связей

- `refines` — уточняет
- `implements` — реализует
- `tests` — покрывает тестом
- `changes` — изменяет
- `depends_on` — зависит от
- `derived_from` — получено из
- `related_to` — связано с

### 9.2 Минимальная логика

- Requirement -> UserStory
- UserStory -> Task
- Requirement -> TestCase
- ChangeRequest -> Requirement / UserStory / Task / TestCase
- DecisionRecord -> Requirement / Task

---

## 10. Набор правил проверки согласованности

MVP должен содержать хотя бы несколько правил.

### 10.1 Примеры правил

1. У каждого approved requirement должен быть источник.
2. У каждой user story должен быть хотя бы один parent requirement.
3. У каждого change request должен быть хотя бы один затронутый артефакт.
4. Requirement без user story — warning.
5. Requirement без test case — warning.
6. Артефакт со статусом archived не должен использоваться как активная версия.
7. Если change request одобрен, то хотя бы один связанный артефакт должен получить новую версию.

## 11. Рабочие сценарии MVP

### 11.1 Сценарий 1. Формализация

Вход:
- свободное описание проекта.

Шаги:
1. пользователь загружает описание;
2. LLM выделяет требования;
3. требования сохраняются как Requirement;
4. из требований создаются UserStory;
5. из требований/историй создаются TestCase;
6. связи сохраняются.

Выход:
- набор связанных артефактов.

### 11.2 Сценарий 2. Изменение

Вход:
- существующий проект с артефактами;
- новый Change Request.

Шаги:
1. пользователь подает change request;
2. система находит связанные артефакты;
3. строит минимальный контекст;
4. LLM анализирует, что нужно менять;
5. система создает новые версии затронутых артефактов;
6. запускается проверка согласованности.

Выход:
- список затронутых артефактов;
- предложения или обновления;
- отчет о согласованности.

## 12. Технологический стек

Ниже приведен реалистичный стек для MVP.

### 12.1 Язык программирования

**Python 3.11+**

Почему:
- удобный и доступный язык;
- хорошая экосистема для LLM и API;
- легко использовать с Claude Code / Codex;
- подходит для быстрого прототипирования.

### 12.2 Бэкенд

**FastAPI**

Почему:
- быстро поднимается;
- удобно строить API;
- хорошо сочетается с Pydantic;
- достаточно легкий для MVP.

### 12.3 Модели данных

**Pydantic**

Почему:
- валидация входных и выходных структур;
- удобно описывать схемы артефактов;
- хорошо интегрируется с FastAPI.

### 12.4 База данных

На старте:
- **SQLite** для локального MVP

Потом:
- **PostgreSQL** для более серьезного развития

Почему:
- SQLite проста для быстрого старта;
- не требует отдельной инфраструктуры;
- легко заменить позже.

### 12.5 ORM / доступ к данным

**SQLAlchemy**

Почему:
- стандартный инструмент;
- удобно описывать сущности и связи;
- масштабируется лучше, чем ручной SQL.

### 12.6 Работа с графом связей

На MVP:
- обычная таблица связей в SQL

Потом опционально:
- **Neo4j** или отдельный графовый слой

Почему:
- на старте отдельная графовая БД не обязательна;
- достаточно таблицы `artifact_links`.

### 12.7 Вызов моделей

На старте:
- **Anthropic API** или **OpenAI API**

Рекомендуется сделать абстрактный адаптер:
- `generate_requirements()`
- `generate_user_stories()`
- `generate_test_cases()`
- `analyze_change_request()`

Почему:
- можно легко менять провайдера;
- код не будет жестко привязан к одной модели.

### 12.8 Интерфейс

Вариант 1:
- **CLI** для самого первого прототипа

Вариант 2:
- **простейший web UI** на FastAPI + Jinja2 / HTMX / маленький frontend

Рекомендация:
- если нужно быстро показать работу — начать с CLI или очень простого web UI.

### 12.9 Хранение и экспорт документов

- JSON в базе как нормализованные записи;
- Markdown-export для просмотра;
- при необходимости позже — DOCX-export.

### 12.10 Тестирование

- **pytest**
- базовые интеграционные тесты workflow
- тесты на validation rules

## 13. Инструменты, которые можно использовать в разработке

### 13.1 Claude Code
Можно использовать для:
- генерации структуры проекта;
- написания моделей данных;
- генерации API;
- написания CRUD-логики;
- тестов;
- рефакторинга.

Важно:

### 13.2 Codex
Можно использовать для:
- генерации отдельных модулей;
- рефакторинга;
- написания тестов;
- параллельной реализации технических кусков.

Не нужен в MVP как обязательная зависимость.

Но позже его можно использовать:
- как внешнюю систему управления агентами;
- как среду для организации работы нескольких агентов;
- как вспомогательную платформу вокруг твоего слоя.

Важно:
твой проект не должен зависеть от Paperclip в своей сути.

## 16. Определение готовности MVP

MVP считается готовым, если он умеет:

1. принять описание проекта;
2. создать набор требований;
3. создать связанные пользовательские истории;
4. создать связанные тест-кейсы;
5. принять change request;
6. показать, какие артефакты затронуты;
7. создать хотя бы часть обновленных версий;
8. выдать отчет о согласованности.

## 17. Основные риски

### 17.1 Слишком широкий объем
Риск: попытка сделать сразу всю “команду из агентов”.

Решение: жестко держать MVP-сценарий.

### 17.2 Плохая модель артефактов
Риск: артефакты описаны слишком размыто.

Решение: зафиксировать минимальный набор типов и связей до начала кодинга.

### 17.3 Слишком абстрактные запросы к Claude/Codex
Риск: агент генерирует хаотичный код.

Решение: дробить работу на маленькие технические шаги.

### 17.4 Переоценка UI
Риск: много времени уйдет на оболочку, а не на ядро.

Решение: сначала CLI или минимальный web UI.

### 17.5 Плохой демо-сценарий
Риск: система существует технически, но не показывает ценность.

Решение: заранее подготовить один хороший сквозной сценарий.

## 18. Рекомендованный демонстрационный сценарий

Для первого показа лучше взять простой и понятный проект, например:

**веб-сервис записи к врачу**  
или  
**интернет-магазин**

Пример:

1. пользователь вводит описание проекта;
2. система выделяет требования;
3. система создает user stories;
4. система создает test cases;
5. пользователь добавляет change request:
   “добавить возможность гостевого оформления заказа”;
6. система показывает затронутые требования, истории и тесты;
7. система предлагает обновления и отчет о согласованности.

## 21. Практическая инструкция для Claude/Codex

Ниже — рекомендуемая постановка задачи для помощника-разработчика.

### 21.1 Краткая постановка

Нужно разработать MVP backend-системы управления проектной памятью для AI-проектов.  
Система должна хранить проектные артефакты, их версии и связи, а также поддерживать сценарий:
- project description -> requirements -> user stories -> test cases -> change request -> impact analysis -> consistency check.

### 21.2 Что требуется на первом этапе

1. FastAPI backend
2. SQLite database
3. SQLAlchemy models:
   - Artifact
   - ArtifactVersion
   - ArtifactLink
   - ChangeLog
4. Pydantic schemas
5. CRUD endpoints
6. Workflow services:
   - generate_requirements
   - generate_user_stories
   - generate_test_cases
   - analyze_change_request
7. Validation service
8. Minimal CLI or web UI for demo

### 21.3 Что важно

- не делать лишнего;
- код должен быть чистым и модульным;
- все сущности должны быть типизированы;
- логика выбора контекста должна быть выделена отдельно;
- LLM provider должен быть абстрагирован;
- нужны простые тесты на workflow и validation rules.

## 23. Итог

Этот проект нужно рассматривать не как “очередную агентную платформу” и не как “чат с памятью”, а как **систему управления памятью проекта через связанные артефакты**.

MVP должен доказать, что:
- проектные знания можно хранить вне модели;
- их можно связать между собой;
- на их основе можно строить узкий и точный контекст;
- это помогает лучше обрабатывать изменения и сохранять согласованность проекта.

Это и есть минимальная, понятная и реализуемая версия идеи.
