## 0. Двухслойный документ: rich-text тело + Items как машиночитаемый слой — высший приоритет

> **Архитектурное решение (зафиксировано):** документ состоит из двух слоёв.
> **Тело** — свободный rich-text, который человек пишет и редактирует как страницу в Confluence.
> **Items** (R1, T1…) — структурированный metadata-слой, который остаётся машиночитаемым
> фундаментом для consistency checks и impact analysis. Items не исчезают — они просто перестают
> быть единственным способом взаимодействия с документом.

### Два пути создания

- **LLM-путь:** LLM генерирует и тело документа, и Items одновременно. Человек затем
  редактирует любой из слоёв по своему усмотрению.
- **Human-путь:** Человек пишет тело документа свободно (и опционально добавляет Items вручную).
  При следующем обращении к LLM она читает текущее содержимое документа и при необходимости
  синхронизирует Items с телом. Если содержимое уже отражено в Items — не трогает.

### Синхронизация Items с телом

Items синхронизируются **только явно** — автоматического фонового обновления нет:
- Пользователь редактирует Items вручную, **или**
- Пользователь запускает LLM-операцию (formalize, change request, кнопка «Sync items») —
  LLM извлекает/обновляет Items из содержимого тела.

Это исключает ситуацию «LLM неожиданно переписала то, что я написал».

### Rich-text редактор (тело документа)

Форматирование: **жирный**, *курсив*, подчёркивание, зачёркивание; цвет шрифта, заливка
(highlight); заголовки **H1–H6**; **toggle** — сворачиваемые блоки (текст и заголовки);
таблицы. Rich-text — приятная фича, не основная цель.

### Связанность документов

Документы остаются связанными независимо от сценария (LLM или человек). При создании или
редактировании — выбор: связать вручную или делегировать LLM. Items с ключами (R1→T1) остаются
машиночитаемыми якорями для consistency checks, impact analysis и поиска по графу.

### Что не меняется в бэкенде

Поле `items` в модели артефакта остаётся как есть. Поле `content` расширяется до rich-text
(markdown или Tiptap JSON). Добавляется одна LLM-операция: `extract_items_from_content(body) → items[]`.
Consistency service и impact analysis не требуют правок — они по-прежнему работают по Items.

Поглощает пункты §3 «Редактирование пунктов в UI» и «Rich-text/Markdown-редактор».

## Debugging — найденные баги и недоработки (аудит Codex, 2026-05-28)

Список того, что нашёл Codex при проходе по репозиторию. Отсортировано примерно по серьёзности.

1. **Build/lint blocker — `react-hooks/refs` в SlashMenu.** `apps/web/src/components/editor/SlashMenu.tsx:79`:
   `itemsRef.current = items`, `indexRef.current = index`, `stateRef.current = state` обновляются прямо
   во время render, что запрещено. `pnpm --filter @engram/web lint` падает с 3 ошибками. Перенести
   синхронизацию refs в `useEffect`/`useLayoutEffect` либо убрать refs через замыкание / стабильный handler.

2. **Rich-text ломает change request.** `apps/api/src/engram/llm/mock.py:146` делает
   `proposed_content=f"{item.content}\n\n— Revised..."`. После нового редактора `content` часто является
   сериализованным Tiptap JSON; такой append превращает валидный JSON в невалидную строку, а
   `apps/web/src/lib/editor/content.ts:35` затем покажет весь JSON как обычный текст. Нужно либо обновлять
   Tiptap JSON структурно, либо передавать LLM plain-text и возвращать согласованный формат.

3. **Свежий checkout может не собраться без локального generated-файла.** Фронтенд импортирует
   `apps/web/src/lib/types.ts:1`, но этот файл исключён в `.gitignore:31`. Локально TypeScript проходит,
   потому что файл есть, но в репозитории его не будет. Нужно либо коммитить generated API types, либо
   генерировать их перед dev/build/lint, либо заменить на ручные shared-типы.

4. **Backend принимает некорректные статусы для типов артефактов.** `apps/api/src/engram/schemas/artifact.py:30`
   (и update) допускают любой `ArtifactStatus` для любого `ArtifactType`. UI ограничивает статусы через
   `STATUSES_FOR_TYPE`, но API спокойно примет, например, `applied` для `requirement`. Риск загрязнения
   данных и некорректной логики consistency/workflows. Нужен backend-валидатор.

5. **UI может показывать stale data после change request.** `apps/web/src/lib/queries.ts:179` инвалидирует
   только `["artifacts"]` и `["all-links"]`, а workflow меняет конкретные артефакты, версии и links. Если
   открыта страница артефакта, `["artifact", id]`, `["versions", id]`, `["links", id]` могут остаться старыми.
   Аналогично `apps/web/src/lib/queries.ts:140` инвалидирует links только для текущего `artifactId`, не для target.

6. **Конфиг по умолчанию расходится с docker-compose.** Backend default DB URL смотрит на `localhost:5432`
   (`apps/api/src/engram/config.py:21`), а docker публикует Postgres на `5433` (`infra/docker-compose.yml:13`).
   `.env.example` правильный, но без `.env` API будет подключаться не туда. Синхронизировать default с
   dev-инфрой или явно падать с понятной ошибкой.

**Проверки на момент аудита:**
- `pnpm --filter @engram/web exec tsc --noEmit --incremental false --pretty false` — прошёл.
- `ruff check .` в `apps/api` — прошёл.

## 1. Сделать вывод по-настоящему умным (реальная LLM)

> Самый заметный для пользователя шаг: меняется только качество текста, структура остаётся.

- Реализовать `llm/anthropic.py` (и/или `llm/openai.py`) за существующим интерфейсом
  `LLMProvider`; переключение через `ENGRAM_LLM_PROVIDER` + ключ в `.env`. ⚠️ платные токены.
- Качественная **семантическая группировка по фичам** (сейчас мок группирует по «весомому» слову).
- Осмысленные требования/истории/задачи: объединение дублей, нормальные формулировки, разумное
  число пунктов.
- Реальные **эмбеддинги** для поиска (локальный `fastembed` уже опционален; облачные — для прода).
- Контроль стоимости: кэширование промптов, батчи, бюджеты токенов.

## 2. Уникальная фишка: AI-связывание и «умная память»

> То, чего нет у Confluence/Notion — ради этого проект и существует.

- **AI-подсказки связей**: эндпоинт `suggest-links` (эмбеддинги + LLM предлагают тип связи между
  артефактами) + UI принятия подсказок. *(было осознанно отложено)*
- **Точечный анализ влияния**: change request бьёт по конкретным пунктам (R3, R5), а не по всему
  документу; новые версии — на уровне пунктов.
- **Авто-починка согласованности**: LLM предлагает недостающую задачу/тест для непокрытого
  требования прямо из отчёта.
- Поиск **дубликатов и противоречий** между пунктами.
- Контекст-ретривер как продукт: отдавать «минимальный контекст» внешним агентам (см. §5 — MCP).

## 3. Глубина авторства и UX («ощущение платформы»)

- Редактирование **пунктов** в UI (добавить/править/переупорядочить), а не только `content`.
- Rich-text/Markdown-редактор; **комментарии и обсуждения** на артефактах.
- Граф получше: авто-раскладка (dagre/elk), фильтры, фокус на узле, рёбра на уровне пунктов.
- **Глобальный поиск** в UI по документам и пунктам (API уже есть).
- Тип **DecisionRecord** (запись о решении) из спецификации.
- Diff между версиями документа в UI.

## 4. Совместная работа и платформа

- **Аутентификация** + пользователи; роли и права доступа.
- **Несколько проектов/воркспейсов** (сейчас один неявный проект).
- Лента активности / журнал изменений в UI; уведомления.
- Реал-тайм обновления (WebSocket/SSE) при совместной работе.

## 5. Интеграции (открыть память наружу)

- **MCP-сервер** поверх Engram: отдавать релевантный контекст кодинг-агентам (Claude Code и т.п.) —
  изначальная идея «слой памяти для агентов».
- **Плагин/встраивание** в Confluence / Jira / Notion / GitHub (изначальная идея проекта как
  расширения существующих платформ).
- Импорт/экспорт: **Markdown-export**, позже **DOCX**; импорт из существующих документов/issue.

## 6. Оркестрация и масштаб

- **LangGraph** за `WorkflowEngine`: ветвление, чекпоинты, **human-in-the-loop** (утверждение
  предложений), стриминг. *(осознанно отложено, пока потоки процедурные)*
- Фоновые/асинхронные воркфлоу для больших проектов.
- Отдельный **графовый слой** (Neo4j), если запросы по связям перерастут SQL.

## 7. Надёжность и эксплуатация

- **CI**: тесты + ruff + build на push; pre-commit хуки.
- **Browser e2e** (Playwright) поверх текущего API-e2e.
- **Деплой**: Docker-образы api+web, прод-compose, управление окружением/секретами.
- **Запушить в git-remote** — сейчас удалёнка не настроена (`gh repo create`, аккаунт `Axx-Axvd`).
- Наблюдаемость: логи, метрики, трейсинг.
- Прод-безопасность: валидация входных данных, rate limiting, секреты.
